## Protocolo verificado

1. Se exige `--browser --submit --confirm-submit ENVIAR`.
2. El portal debe pertenecer a la lista explícita de adaptadores habilitados.
3. Antes del navegador se escribe un registro atómico `en_progreso`.
4. El adaptador valida nuevamente el dominio después de posibles redirecciones.
5. Si existe clic final y confirmación visible, el registro queda `confirmado`.
6. Si hubo clic pero no confirmación, excepción o cierre inesperado, queda `incierto`.
7. `confirmado`, `incierto` y un `en_progreso` abandonado bloquean una segunda ejecución.
8. Un fallo estructurado anterior al clic libera la reserva y permite reintento.
9. La captura se actualiza después del intento para conservar la respuesta visible del portal.

## Hallazgos TDD

La implementación anterior registraba el envío solamente después de regresar del navegador. Un cierre entre el clic y el guardado permitía repetir una solicitud potencialmente enviada. El registro previo elimina esa ventana.

También se añadió validación del dominio final. Una redirección a un host no asociado con el portal detiene el flujo antes de buscar el botón de envío.

## Limites

No se realizó ningún envío real. Los estados del navegador fueron simulados con adaptadores deterministas y se verificó por separado la sintaxis del script Node.

## Veredicto
